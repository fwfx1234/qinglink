# QingLink 协议 v2

> 完整的上行请求类型列表（95 个 `WsClientRequest` 变体、载荷字段与错误码）见
> [`requests.md`](requests.md)。本文按主题讲语义，不复述类型清单。

服务发现使用 UDP `3723` 广播请求，响应包含 `id`、`name`、`version=2`、`port` 与可选的 `mac`（供唤醒使用）。

未认证端点：

- `GET /api/v2/health`
- `POST /api/v2/pairing/requests`
- `POST /api/v2/pairing/confirm`
- `DELETE /api/v2/pairing/requests/{request_id}`

`GET /api/v2/health` 返回 `pc_id`、`name`、`version`（协议版本，固定 `2`）、`port` 与
`app_version`。`app_version` 是服务端产品版本号，形如 `0.1.0+13`：`+` 之前是
`Cargo.toml` 的语义版本，之后是随源码改动自增的构建号。它是**可选字段**——旧版服务
不返回，客户端必须容忍缺失，且不得把缺失当成空字符串（缺失表示"服务端版本未知"）。

已认证控制使用 `WS /api/v2/events`；高频指针输入使用 `WS /api/v2/input`。每个 JSON 命令都包含 `request_id`，响应使用 `{type, request_id, data}` —— **信封里只有一个 `data`，没有顶层 `error` 键**。错误帧同样是 `data`：

```json
{"type": "error", "request_id": "r1", "data": {"code": "REVOKED", "message": "设备授权已失效"}}
```

这一点由服务端的 `#[serde(tag = "type", content = "data")]` 决定，不是实现细节。**HTTP 契约与它不同**：HTTP 用 `{"ok": false, "error": {"code", "message"}}`（配对的 `/api/v2/pairing/*` 等都走这个）。两套信封的字段名**不可互换**——把 HTTP 的 `error` 套到 WS 帧上会读到一个永远为 `null` 的字段，从而丢掉全部错误码；反过来把 WS 的 `data` 套到 HTTP 上则会让成功响应的 `data` 被当成错误。

远程输入在普通桌面上使用 `send_text` 提交 UTF-8 文本，使用 `key_event` 发送 HID usage 事件（`usage`、`modifiers`、`pressed`）。Windows 安全桌面有意拒绝 Unicode 文本；客户端应在此处使用标准键盘 usage。鼠标移动保持 12 字节二进制帧，而按钮和滚轮命令在两种桌面路径上都可用。

安全桌面控制增加了 `get_secure_desktop_status`、`secure_attention` 和 `send_secure_ascii`。后者仅接受可打印 ASCII 并通过活动的 Windows 键盘布局映射；它从不使用剪贴板。安全注意命令受服务器速率限制，仅对已认证的已配对设备可用。当前 v2 传输在本地网络上仍为 WS/HTTP；在添加 TLS/WSS 之前，部署必须将网络视为可信的。

对于 UAC 和安全桌面交互，客户端应：
1. 轮询 `get_secure_desktop_status` 以检测桌面何时切换到 `uac` 或 `winlogon`。
2. 在 UAC 对话框上使用 `mouse_move_absolute` 进行精确按钮点击，因为相对 `mouse_move` 无法可靠地定位特定屏幕坐标。
3. 在安全桌面上使用带标准 HID usage 的 `key_event` 进行键盘输入；`send_text` 在此处被拒绝。
4. `secure_desktop_status` 响应包含 `uac_detected` 和 `token_integrity_level` 字段，以帮助客户端决定当前令牌是否可以进行 UAC 交互。

在 Windows 10/11 x64 上，监听器和令牌存储由自动 LocalSystem `QingLinkService` 拥有。持久化数据存储在 `%ProgramData%\QingLink` 中；其目录 ACL 仅向 SYSTEM 和内置管理员组授予完全访问权限。服务为活动的控制台 WTS 会话维护一个输入代理，不注入到其他用户会话中。现有令牌可以在登录前进行身份验证。创建新配对仍然是桌面确认的操作，不作为无人值守的登录前注册路径暴露。

## 配对

手机创建请求并保留返回的标识符，同时 PC 显示验证码：

```json
POST /api/v2/pairing/requests
{"device_id":"mobile-...","device_name":"轻联手机"}

{"request_id":"uuid","expires_at_unix":0}
```

请求本身**不授予任何权限**，响应里永远没有 `token`；令牌只能由随后的验证码确认下发。
`device_id` / `device_name` 必须非空且不超过 128 字节，同一台 PC 上待确认的请求上限为
128 个。创建请求还要求桌面上有**已解锁且 2 秒内活跃**的桌面端：桌面端未运行或处于锁屏
时，接口固定返回 423 `PAIRING_REQUIRES_DESKTOP`，不做无人值守注册。

手机在 60 秒截止时间前确认验证码。成功响应包含稳定的 PC 标识和长期令牌；令牌由移动应用存储在平台安全存储中。

```json
POST /api/v2/pairing/confirm
{"request_id":"uuid","pin":"123456","device_id":"mobile-...","device_name":"轻联手机"}

{"token":"...","pc_id":"...","pc_name":"办公室电脑","mac_address":"AA:BB:CC:DD:EE:FF","wake_networks":[{"mac_address":"AA:BB:CC:DD:EE:FF","ipv4_address":"192.168.1.42","prefix_length":24,"broadcast_address":"192.168.1.255"}]}
```

`device_id` 必须与创建请求时的一致，否则在消耗验证码尝试次数之前就返回
400 `DEVICE_MISMATCH`；`pin` 必须是 6 位数字。

配对错误使用稳定错误码（HTTP 状态在括号内）：
`PAIRING_NOT_FOUND`(404)、`PAIRING_EXPIRED`(410)、`INVALID_PIN`(400)、
`RATE_LIMITED`(429)、`DEVICE_MISMATCH`(400)、`INVALID_REQUEST`(400)、
`PAIRING_BUSY`(429)、`PAIRING_REQUIRES_DESKTOP`(423)、
`PAIRING_UNAVAILABLE`(500)、`TOKEN_CREATE_FAILED`(500)。
错误响应体统一为 `{"ok":false,"error":{"code":...,"message":...}}`，客户端必须按
`code` 分支，不要解析 `message`。

## 会话关闭

服务端需要主动结束已认证会话时，先下发一条事件再关闭连接：

```json
{"type":"session_closed","data":{"code":"SERVICE_PAUSED"}}
```

| `code` | 含义 | 客户端应有行为 |
| --- | --- | --- |
| `REVOKED` | 该设备令牌已被撤销 | 清除本地令牌，回到配对流程 |
| `REPLACED` | 同一令牌在别处登录，本会话被顶替 | 提示"已在其他客户端登录"，不自动重连 |
| `SERVICE_PAUSED` | 桌面端暂停了远程控制 | 保留令牌，退避重连；服务恢复后自动连回 |
| `SERVICE_STOPPING` | 服务正在停用/停机，监听器已收回 | 同上 |

服务暂停期间监听器不绑定端口，任何请求都会失败或返回错误码 `SERVICE_PAUSED`；
恢复后需要客户端自行重连，服务端不会主动回连。

## 前台窗口与焦点文本

`get_foreground` 返回前台窗口信息，并额外带上焦点输入框里**已有的文本**：

```json
{"type":"get_foreground","request_id":"req-4"}

{"type":"foreground","request_id":"req-4","data":{"pid":1234,"title":"记事本 - 未命名","path":"C:\\Windows\\notepad.exe","process_name":"notepad.exe","hwnd":131234,"focus_text":"现有的文字"}}
```

| 字段 | 含义 |
| --- | --- |
| `pid` / `title` / `path` / `process_name` / `hwnd` | 前台窗口与所属进程 |
| `focus_text` | 焦点输入框的已有文本；**省略**表示没有可回填的输入框 |

`focus_text` 由 UI Automation 读取，取值口径是"**只认编辑框的 Value 模式**"：

- 只接受 `Edit` 控件（`UIA_EditControlTypeId`）且必须提供 `ValuePattern`。`ComboBox`
  读出来的是选中项、`Document` 读出来的是整页正文、只暴露文本树（`TextPattern`）的自绘
  控件读出来可能混入占位提示——这些都**不返回**（`focus_text` 省略）。因此 Word/WPS 正文、
  终端缓冲区、以及微信这类只暴露文本树的输入框都不会回填。
- Chromium 系（`FrameworkId` 为 `Chrome`：Chrome / Edge / Electron / WebView2）另加一条
  **结构判据**：焦点 `Edit` 若带子元素，视为富文本编辑器（contenteditable），其 `Value`
  可能混着占位提示且无法与正文区分，`focus_text` 省略；纯 `<input>` / `<textarea>` 在可访问性
  树里是叶子节点，地址栏、搜索框与普通表单**照旧回填**。
- 密码框、只读控件、禁用控件恒不返回，客户端不得尝试回填；
- 焦点不在编辑框上、或读取失败时同样省略；
- 取到的值为空白、或**空白归一后**与控件的可访问名/帮助文字相同（典型是 Chromium 把
  `placeholder` 算成可访问名）时，按"占位提示"处理，也返回省略；
- 长度上限 4096 字符。客户端拿到后可把它当作输入框的初始内容，但**不能假设**它一定与
  PC 侧光标位置一致——回填后按"整体重写"处理中间编辑是允许的。

客户端每次打开输入面板都应当**重新请求一次** `get_foreground` 并只用这一次的结果：请求失败
时必须按空基线处理，不得复用上一次的 `focus_text`，否则会把别的窗口的文字回填进来。

旧版服务端不返回该字段，客户端按"未知/空"处理即可。

## 事件推送

服务端在已认证的控制通道上主动推送事件，客户端按 `type` 分辨。除既有的
`foreground_changed` / `process_started` / `process_ended` / `system_*` /
`launcher_catalog_ready` / `session_closed` 外，还包括：

```json
{"type":"input_state","left":true,"right":false,"middle":false}
```

`input_state` 表示 PC 侧鼠标左右中键**当前是否处于按下状态**（物理按压与远端注入合并后的
事实）。服务端在状态变化时立即推送，并每 10 秒补发一次，让后连上来的客户端在一个周期内
对齐。客户端可以用它在触控板上提示"PC 侧左键按住"，并在开始拖拽时避免重复下发按下。

### 焦点进入输入框

```json
{"type":"focus_input"}
```

`focus_input` 表示 PC 的焦点**第一次**落进可编辑控件（编辑框、组合框、文档控件，**密码框也算**），
用于让手机端自动弹出键盘面板、把手机当输入工具。

- **只在边沿推送**：PC 侧用 `EVENT_OBJECT_FOCUS` 监听焦点，只在"上一次没有焦点、这次有焦点"
  时下发一次；焦点一直停在同一个输入框里、或离开输入框，都**不再推送**。因此客户端不需要
  去重或冷却。
- 不携带内容。要回填文本仍用 `get_foreground` 的 `focus_text`（密码框依旧省略）。
- 事件由桌面端的会话代理产生，服务端只做中继；代理没运行时收不到该事件（其他功能不受影响）。
- 旧版服务端不推送该事件，客户端收不到即可，不影响其他功能。

## 进程图标

进程列表（`get_processes`）本身**不携带图标**：一页几十行会把每次搜索和下拉刷新
的载荷放大到几百 KiB。图标按行按需取，按 PID 请求：

```json
{"type":"get_process_icon","pid":1234,"request_id":"req-1"}

{"type":"process_icon","request_id":"req-1","data":{"pid":1234,"source":"executable","icon_path":"C:\\Program Files\\Google\\Chrome\\chrome.exe","icon_base64":"iVBORw0KG..."}}
```

解析顺序固定为：程序内嵌图标资源（`source: executable`）→ 程序同目录的 PNG/ICO
等素材（`source: image`）。**不使用外壳默认图标**：一台机器上所有没有自带图标的
进程（svchost.exe、conhost.exe 之类）都会得到同一个通用图标，对进程列表是噪声；
客户端在这些行上保留自己的占位图标即可。

| `source` | 含义 | `icon_base64` |
| --- | --- | --- |
| `executable` | 图标来自程序内嵌资源 | 有 |
| `image` | 图标来自程序同目录的素材文件 | 有 |
| `none` | 进程不存在、路径不可读或没有自带图标 | 省略 |

`source: "none"` **不是错误**：进程可能刚好退出、被保护或本来就没有图标，客户端
保留占位图标即可，不需要提示用户。图标与目录条目同源：默认 128×128 正方形、素材
铺满画布，超出体积预算时服务端会先降边长重新编码，仍超预算才返回 `none`。

服务端按可执行文件路径缓存解析结果（同一程序只解析一次，正结果长期有效、负结果
数分钟后重试），因此重复请求同一程序的多个 PID 是廉价的；客户端同样应按路径去重，
无需为同一个 exe 的每个 PID 各请求一次。标识这条命令的消息类型不在能力协商范围内：
旧版服务端会回 `INVALID_REQUEST`，客户端收到错误后保留占位图标即可。

## 图标预览

手机端的换图标面板要列出条目附近的候选图标文件（`list_scanner_app_icons`），并允许用户
浏览 PC 上任意目录里的图片。这些文件都在 PC 上，手机看不到内容，所以每一项按需取一次预览：

```json
{"type":"get_icon_preview","path":"D:\\Pictures\\logo.png","request_id":"req-3"}

{"type":"icon_preview","request_id":"req-3","data":{"path":"D:\\Pictures\\logo.png","icon_base64":"iVBORw0KG..."}}
```

- **只读**：不落库、不改动任何条目。真正换图标仍用 `refresh_scanner_app_icon`
  （带 `icon_path`）或 `set_scanner_app_icon`。
- 接受的类型只有图标管线能解码的那些：`png` / `jpg` / `jpeg` / `bmp` / `ico`，以及程序和
  快捷方式（`exe` / `lnk`，取它们的内嵌图标资源）。其余类型直接回空载荷。
- 文件不存在、体积为 0 或超过 16 MiB 时同样回空载荷。`icon_base64` 省略表示"这个文件没有
  可用预览"，客户端保留占位图即可，**不是错误**。
- 返回的 PNG 恒为 128×128 正方形，与目录条目、进程图标共用同一套规范化与体积预算。
- 旧版服务端不认识这条命令，会回 `INVALID_REQUEST`；客户端让缩略图退回占位图即可。

## 保持唤醒

控制中心可以远程阻止 PC 自动休眠与显示器熄屏。请求走已认证的控制通道
（`WS /api/v2/events`）。桌面端托盘与管理界面设置页经桌面管理 IPC 的
`set_keep_awake` 命令读写**同一个**开关：开关只由 `QingLinkService` 进程持有，
桌面端不再自己调用 `SetThreadExecutionState`，也不再保存独立偏好。
桌面端通过管理快照的 `keep_awake` 字段跟随状态变化，客户端每次打开控制中心
都应重新读取，不要缓存状态。

```json
{"type":"get_keep_awake","request_id":"req-20"}

{"type":"keep_awake_status","request_id":"req-20","data":{"enabled":true}}
```

```json
{"type":"set_keep_awake","enabled":true,"request_id":"req-21"}

{"type":"keep_awake_status","request_id":"req-21","data":{"enabled":true}}
```

| 消息 | 方向 | 字段 | 说明 |
| --- | --- | --- | --- |
| `get_keep_awake` | 手机 → PC | 无 | 读取服务进程当前开关 |
| `set_keep_awake` | 手机 → PC | `enabled`（bool，必填） | 开启或关闭；回包仍为 `keep_awake_status` |
| `keep_awake_status` | PC → 手机 | `data.enabled`（bool） | 当前生效的开关状态 |

| 错误码 | 触发条件 |
| --- | --- |
| `KEEP_AWAKE_FAILED` | 常驻线程不可用/已退出、`SetThreadExecutionState` 调用失败，或非 Windows 平台 |
| `INVALID_REQUEST` | 旧版服务端不认识这两条命令，或 `set_keep_awake` 缺少 `enabled` |

约束与语义：

- `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED | ES_DISPLAY_REQUIRED)`
  是 **per-thread** 状态，哪个线程调用就归哪个线程持有，线程退出时请求自动失效。服务端用
  一条专用常驻线程（`qinglink-keep-awake`）串行执行所有开关，避免在 `spawn_blocking`
  的工作线程上调用导致状态随线程回收而丢失、或开与关落在不同线程上互相抵消。
- 开关持久化在服务数据库的 `settings.power.keep_awake`，服务启动时按该值恢复；
  `get_keep_awake` 始终返回真实状态，客户端应以此为准。桌面端重启或退出不会
  取消服务持有的请求，桌面端旧偏好键 `power.keep_awake` 已不再使用。桌面端按管理快照的
  `keep_awake` 字段显示状态，快照变化（含手机端切换）由 `ServiceEvent::KeepAwake` 推给
  设置页与托盘。
- 桌面管理 IPC 新增 `set_keep_awake`（`enabled`，返回生效值），能力位
  `keep_awake` 为 `false` 时桌面端把开关判为不支持；管理快照 `keep_awake`
  为可选布尔值，旧服务不返回时桌面端保持原显示值。
- 旧版服务端不认识这两条命令会回 `INVALID_REQUEST`，客户端应把开关置为不可用并提示升级。

## 显示设置

`get_displays` 返回**所有**连接到桌面的显示器，每台都带它的当前模式和**手机端可选模式**：

- 只保留 **1080p 及以上**的模式（`宽 ≥ 1920` 且 `高 ≥ 1080`），不设上限：`1920×1080`、
  `2560×1440`、`2560×1600`、`3440×1440`、`3840×2160`、`4096×2160` 等**真实枚举到**的
  分辨率都会出现，不再按固定白名单裁剪；整台显示器连 1080p 都拿不出来时（老设备）取消
  这层过滤，否则列表会空；
- 每条候选都必须是该显示器**真实枚举到**的组合，服务端不会凭空合成刷新率；
- 同一分辨率下按整 Hz 归档刷新率，相差 1Hz 以内视为同一档（`DEVMODEW` 只有整数 Hz，
  59.94Hz 会报成 `59`，与同一块屏的 `60` 合并），每档分辨率最多返回 **4** 条，
  优先当前生效的那条，否则保留 `refresh_millihz` 更大的（`60000` 胜过 `59940`）；
- 当前模式不在上述范围内时（如 `1280×720`、`1680×1050`、`5120×1440`），也会原样附在
  列表里，保证客户端能高亮、能切回来。

> 枚举必须走到驱动返回失败为止。早期实现把上限写死成 256 条并静默截断，而 Windows 按
> 分辨率从小到大返回模式，4K@120 的面板实测有 705 条——手机端因此只剩两个低分辨率。

```json
{"type":"get_displays","request_id":"req-8"}

{"type":"displays","request_id":"req-8","data":{"displays":[
  {
    "id":"\\\\.\\DISPLAY1",
    "name":"通用即插即用监视器",
    "primary":true,
    "current_mode":{"width":3840,"height":2160,"refresh_millihz":120000},
    "modes":[
      {"width":4096,"height":2160,"refresh_millihz":60000},
      {"width":3840,"height":2160,"refresh_millihz":120000},
      {"width":3840,"height":2160,"refresh_millihz":60000},
      {"width":2560,"height":1600,"refresh_millihz":120000},
      {"width":2560,"height":1440,"refresh_millihz":120000},
      {"width":1920,"height":1080,"refresh_millihz":120000},
      {"width":1920,"height":1080,"refresh_millihz":60000}
    ]
  }
]}}
```

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `displays[].id` | string | 显示器标识，形如 `\\.\DISPLAY1`，切模式时原样回传 |
| `displays[].name` | string | 显示器名称 |
| `displays[].primary` | bool | 是否主显示器 |
| `displays[].current_mode` | object | 当前生效的模式，字段同下面的模式对象 |
| `displays[].modes` | array | 1080p 及以上的可选模式 + 当前模式（若不在列表内），按面积降序、同分辨率刷新率降序排列 |
| `modes[].width` / `height` | integer | 分辨率，单位像素 |
| `modes[].refresh_millihz` | integer | 刷新率，单位**毫赫兹**（`60000` 表示 60Hz，`59940` 表示 59.94Hz） |

切换模式使用扁平的四个字段（不是嵌套的 `mode` 对象）：

```json
{"type":"set_display_mode","display_id":"\\\\.\\DISPLAY1",
 "width":2560,"height":1440,"refresh_millihz":120000,"request_id":"req-9"}

{"type":"success","request_id":"req-9"}
```

`refresh_millihz` 必须与 `modes` 里给出的值**逐位相同**：客户端应当把列表里的值原样回传，
不要自己四舍五入到整百毫赫兹，否则会被判为不支持。典型例子是只枚举到 `59940` 的面板——
传 `60000` 会被拒绝，必须原样回传 `59940`。

校验对象是显示器**枚举到的全部模式**，不是 `modes` 候选列表。因此 `modes` 之外的模式
（旧版本保存的 `3440×1440`、`59.94Hz` 等，以及游戏启动前的快照恢复）仍然可以设置。

| 错误码 | 触发条件 |
| --- | --- |
| `DISPLAY_LIST_FAILED` | 完全没有检测到已连接显示器，或检测到却读不出当前模式；枚举由用户会话里的会话代理执行，代理不可用时同样返回该码 |
| `DISPLAY_SET_FAILED` | 目标模式不在该显示器枚举到的模式集合里、显示驱动拒绝，或该切换需要重启 |

切换成功后客户端应重新调用一次 `get_displays` 确认实际生效的模式——Windows 可能
在 15 秒确认期内回滚，`success` 只表示"这次调用被接受"。

## 游戏启动显示模式

`list_launcher_items` 与 `get_recent_launcher_items` 的游戏摘要可包含 `launch_mode`：

```json
{"width":2560,"height":1440,"refresh_millihz":60000}
```

手机端通过 `get_displays` 读取显示器（通常是主显示器）的可用模式，并用 `update_scanner_app`
持久化配置。省略 `launch_mode` 表示不修改现有配置；`clear_launch_mode: true` 清除配置。
设置值必须是主显示器 `modes` 候选里的宽、高和刷新率组合，否则服务端返回
`INVALID_DISPLAY_MODE`。候选集合就是上面「显示设置」的 1080p 及以上模式，因此超出该范围的旧配置
（例如 `1280×720`、`1024×768`）在启动时仍会切换与恢复，但手机端不会再把它标成已选，也无法重新保存。

启动已配置的游戏时，服务端先保存主显示器当前模式，再尝试切换并启动游戏。切换失败时仍会
启动游戏。服务端按启动前后的 PID 差异识别游戏可执行文件，跟踪它及其子进程，最后一个已配置
游戏进程退出后恢复原模式；同时启动多个已配置游戏时，以最先启动的游戏模式为准。手机端
`launch_scanner_app` 与本机管理界面的 `POST /apps/launch` 走**同一个协调器**，所以两边启动
同一游戏的效果一致。服务重启后会按已保存的游戏路径重新接管进程监视，若 180 秒内没发现游戏
进程则直接恢复模式。快照存在服务数据库 `settings` 表的 `launch_display.snapshot` 键下，
恢复失败时保留快照供下次启动重试。

## 目录扫描

`refresh_launcher_catalog`、`refresh_steam_games`、`scan_game_directory` 都会先检查
"是否允许扫描"：检测到游戏在运行时，扫描会打扰前台游戏，因此一律拒绝。

| 错误码 | 触发条件 | 文案 |
| --- | --- | --- |
| `GAME_ACTIVE` | 检测到游戏进程正在运行（`refresh_launcher_catalog` / `refresh_steam_games`）；`scan_game_directory` 同样受此限制 | 目录扫描为"检测到游戏运行，扫描已延后"；Steam 扫描为"检测到游戏运行，Steam 扫描已延后" |

`GAME_ACTIVE` 是**可重试**的临时拒绝，不是配置错误：客户端应把服务端文案直接展示给
用户（"稍后再扫"），不要重试、也不要清空本地目录。手机端在扫描动作里已按此处理。

## UDP 发现

客户端向局域网广播 UDP `3723` 的 `qinglink-discover-v1` 请求。服务仅在 TCP `3721` 就绪时响应 JSON，包含持久化 `id`、显示名称、协议版本和 TCP 端口。客户端按 `id` 去重，并在 PC 更换网络时替换地址。

## 认证

配对后，两个 WebSocket 通道都需要令牌认证消息。旧版 PIN 认证消息和所有 `/api/v1/*` 端点有意不被支持。
