# QingLink 协议 v2

服务发现使用 UDP `3723` 广播请求，响应包含 `id`、`name`、`version=2`、`port` 和 `pairing`。

未认证端点：

- `GET /api/v2/health`
- `POST /api/v2/pairing/requests`
- `POST /api/v2/pairing/confirm`
- `DELETE /api/v2/pairing/requests/{request_id}`

已认证控制使用 `WS /api/v2/events`；高频指针输入使用 `WS /api/v2/input`。每个 JSON 命令都包含 `request_id`，响应使用 `{type, request_id, data|error}`。

远程输入在普通桌面上使用 `send_text` 提交 UTF-8 文本，使用 `key_event` 发送 HID usage 事件（`usage`、`modifiers`、`pressed`）。Windows 安全桌面有意拒绝 Unicode 文本；客户端应在此处使用标准键盘 usage。鼠标移动保持 12 字节二进制帧，而按钮和滚轮命令在两种桌面路径上都可用。

安全桌面控制增加了 `get_secure_desktop_status`、`secure_attention` 和 `send_secure_ascii`。后者仅接受可打印 ASCII 并通过活动的 Windows 键盘布局映射；它从不使用剪贴板。安全注意命令受服务器速率限制，仅对已认证的已配对设备可用。当前 v2 传输在本地网络上仍为 WS/HTTP；在添加 TLS/WSS 之前，部署必须将网络视为可信的。

对于 UAC 和安全桌面交互，客户端应：
1. 轮询 `get_secure_desktop_status` 以检测桌面何时切换到 `uac` 或 `winlogon`。
2. 在 UAC 对话框上使用 `mouse_move_absolute` 进行精确按钮点击，因为相对 `mouse_move` 无法可靠地定位特定屏幕坐标。
3. 在安全桌面上使用带标准 HID usage 的 `key_event` 进行键盘输入；`send_text` 在此处被拒绝。
4. `secure_desktop_status` 响应包含 `uac_detected` 和 `token_integrity_level` 字段，以帮助客户端决定当前令牌是否可以进行 UAC 交互。

在 Windows 10/11 x64 上，监听器和令牌存储由自动 LocalSystem `QingLinkService` 拥有。持久化数据存储在 `%ProgramData%\QingLink` 中；其目录 ACL 仅向 SYSTEM 和内置管理员组授予完全访问权限。服务为活动的控制台 WTS 会话维护一个输入代理，不注入到其他用户会话中。现有令牌可以在登录前进行身份验证。创建新配对仍然是桌面确认的操作，不作为无人值守的登录前注册路径暴露。

## 配对

手机创建请求并保留返回的标识符，同时 PC 显示验证码：

```json
POST /api/v2/pairing/requests
{"device_id":"mobile-...","device_name":"轻联手机"}

{"request_id":"uuid","expires_at_unix":0}
```

请求本身**不授予任何权限**，响应里永远没有 `token`；令牌只能由随后的验证码确认下发。
`device_id` / `device_name` 必须非空且不超过 128 字节，同一台 PC 上待确认的请求上限为
128 个。创建请求还要求桌面上有**已解锁且 2 秒内活跃**的桌面端：桌面端未运行或处于锁屏
时，接口固定返回 423 `PAIRING_REQUIRES_DESKTOP`，不做无人值守注册。

手机在 60 秒截止时间前确认验证码。成功响应包含稳定的 PC 标识和长期令牌；令牌由移动应用存储在平台安全存储中。

```json
POST /api/v2/pairing/confirm
{"request_id":"uuid","pin":"123456","device_id":"mobile-...","device_name":"轻联手机"}

{"token":"...","pc_id":"...","pc_name":"办公室电脑","mac_address":"AA:BB:CC:DD:EE:FF","wake_networks":[{"mac_address":"AA:BB:CC:DD:EE:FF","ipv4_address":"192.168.1.42","prefix_length":24,"broadcast_address":"192.168.1.255"}]}
```

`device_id` 必须与创建请求时的一致，否则在消耗验证码尝试次数之前就返回
400 `DEVICE_MISMATCH`；`pin` 必须是 6 位数字。

配对错误使用稳定错误码（HTTP 状态在括号内）：
`PAIRING_NOT_FOUND`(404)、`PAIRING_EXPIRED`(410)、`INVALID_PIN`(400)、
`RATE_LIMITED`(429)、`DEVICE_MISMATCH`(400)、`INVALID_REQUEST`(400)、
`PAIRING_BUSY`(429)、`PAIRING_REQUIRES_DESKTOP`(423)、
`PAIRING_UNAVAILABLE`(500)、`TOKEN_CREATE_FAILED`(500)。
错误响应体统一为 `{"ok":false,"error":{"code":...,"message":...}}`，客户端必须按
`code` 分支，不要解析 `message`。

## 会话关闭

服务端需要主动结束已认证会话时，先下发一条事件再关闭连接：

```json
{"type":"session_closed","data":{"code":"SERVICE_PAUSED"}}
```

| `code` | 含义 | 客户端应有行为 |
| --- | --- | --- |
| `REVOKED` | 该设备令牌已被撤销 | 清除本地令牌，回到配对流程 |
| `REPLACED` | 同一令牌在别处登录，本会话被顶替 | 提示"已在其他客户端登录"，不自动重连 |
| `SERVICE_PAUSED` | 桌面端暂停了远程控制 | 保留令牌，退避重连；服务恢复后自动连回 |
| `SERVICE_STOPPING` | 服务正在停用/停机，监听器已收回 | 同上 |

服务暂停期间监听器不绑定端口，任何请求都会失败或返回错误码 `SERVICE_PAUSED`；
恢复后需要客户端自行重连，服务端不会主动回连。

## 进程图标

进程列表（`get_processes`）本身**不携带图标**：一页几十行会把每次搜索和下拉刷新
的载荷放大到几百 KiB。图标按行按需取，按 PID 请求：

```json
{"type":"get_process_icon","pid":1234,"request_id":"req-1"}

{"type":"process_icon","request_id":"req-1","data":{"pid":1234,"source":"executable","icon_path":"C:\\Program Files\\Google\\Chrome\\chrome.exe","icon_base64":"iVBORw0KG..."}}
```

解析顺序固定为：程序内嵌图标资源（`source: executable`）→ 程序同目录的 PNG/ICO
等素材（`source: image`）。**不使用外壳默认图标**：一台机器上所有没有自带图标的
进程（svchost.exe、conhost.exe 之类）都会得到同一个通用图标，对进程列表是噪声；
客户端在这些行上保留自己的占位图标即可。

| `source` | 含义 | `icon_base64` |
| --- | --- | --- |
| `executable` | 图标来自程序内嵌资源 | 有 |
| `image` | 图标来自程序同目录的素材文件 | 有 |
| `none` | 进程不存在、路径不可读或没有自带图标 | 省略 |

`source: "none"` **不是错误**：进程可能刚好退出、被保护或本来就没有图标，客户端
保留占位图标即可，不需要提示用户。图标与目录条目同源：默认 128×128 正方形、素材
铺满画布，超出体积预算时服务端会先降边长重新编码，仍超预算才返回 `none`。

服务端按可执行文件路径缓存解析结果（同一程序只解析一次，正结果长期有效、负结果
数分钟后重试），因此重复请求同一程序的多个 PID 是廉价的；客户端同样应按路径去重，
无需为同一个 exe 的每个 PID 各请求一次。标识这条命令的消息类型不在能力协商范围内：
旧版服务端会回 `INVALID_REQUEST`，客户端收到错误后保留占位图标即可。

## 图标预览

手机端的换图标面板要列出条目附近的候选图标文件（`list_scanner_app_icons`），并允许用户
浏览 PC 上任意目录里的图片。这些文件都在 PC 上，手机看不到内容，所以每一项按需取一次预览：

```json
{"type":"get_icon_preview","path":"D:\\Pictures\\logo.png","request_id":"req-3"}

{"type":"icon_preview","request_id":"req-3","data":{"path":"D:\\Pictures\\logo.png","icon_base64":"iVBORw0KG..."}}
```

- **只读**：不落库、不改动任何条目。真正换图标仍用 `refresh_scanner_app_icon`
  （带 `icon_path`）或 `set_scanner_app_icon`。
- 接受的类型只有图标管线能解码的那些：`png` / `jpg` / `jpeg` / `bmp` / `ico`，以及程序和
  快捷方式（`exe` / `lnk`，取它们的内嵌图标资源）。其余类型直接回空载荷。
- 文件不存在、体积为 0 或超过 16 MiB 时同样回空载荷。`icon_base64` 省略表示"这个文件没有
  可用预览"，客户端保留占位图即可，**不是错误**。
- 返回的 PNG 恒为 128×128 正方形，与目录条目、进程图标共用同一套规范化与体积预算。
- 旧版服务端不认识这条命令，会回 `INVALID_REQUEST`；客户端让缩略图退回占位图即可。

## 游戏启动显示模式

`list_launcher_items` 与 `get_recent_launcher_items` 的游戏摘要可包含 `launch_mode`：

```json
{"width":2560,"height":1440,"refresh_millihz":60000}
```

手机端通过 `get_displays` 读取主显示器的可用模式，并用 `update_scanner_app` 持久化配置。
省略 `launch_mode` 表示不修改现有配置；`clear_launch_mode: true` 清除配置。设置值必须是
主显示器当前支持的宽、高和刷新率组合，否则服务端返回 `INVALID_DISPLAY_MODE`。

启动已配置的游戏时，服务端先保存主显示器当前模式，再尝试切换并启动游戏。切换失败时仍会
启动游戏。服务端跟踪新出现的游戏进程及其子进程，最后一个已配置游戏进程退出后恢复原模式；
同时启动多个已配置游戏时，以最先启动的游戏模式为准。服务重启后会尝试恢复持久化快照。

## UDP 发现

客户端向局域网广播 UDP `3723` 的 `qinglink-discover-v1` 请求。服务仅在 TCP `3721` 就绪时响应 JSON，包含持久化 `id`、显示名称、协议版本和 TCP 端口。客户端按 `id` 去重，并在 PC 更换网络时替换地址。

## 认证

配对后，两个 WebSocket 通道都需要令牌认证消息。旧版 PIN 认证消息和所有 `/api/v1/*` 端点有意不被支持。
